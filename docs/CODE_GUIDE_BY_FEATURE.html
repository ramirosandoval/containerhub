ContainerHub: el código, pantalla por pantalla

Guía de lectura del árbol de trabajo · 23 de septiembre de 2026 · Sin modificar la aplicación. Complementa la guía de despliegue.

Idea central: una pantalla Vue presenta datos; un provider traduce paginación y filtros a peticiones; Fastify comprueba permisos y entrega trabajo a servicios que leen Docker o integraciones externas. Las configuraciones de identidad y monitorización se guardan en la base configurada. Aquí se explica qué ruta hace qué y dónde seguir el flujo, no cada línea de sintaxis.

Mapa y vocabulario

URL del navegador → router de Vue → página/componente
                                  ↓
                           provider / rest.ts
                                  ↓ HTTP o WebSocket
                           ruta Fastify + permiso
                                  ↓
                         servicio de dominio → Docker / agente / GitLab / Registry / base de datos

Stack: grupo de servicios etiquetados por Swarm. Servicio: especificación que Docker mantiene con sus réplicas. Tarea: intento concreto de ejecutar una réplica en un nodo; puede quedar en el historial. Agente: proceso en cada worker elegible que permite consultar el Docker daemon de ese nodo. CRUD: aquí suele significar tabla/configuración reutilizable de Drax, no permiso implícito de crear o borrar: varias tablas son solo de lectura.

Punto de entrada visual: packages/containerhub-front/src/router/index.ts y packages/containerhub-front/src/navigation.ts. Frontend: packages/containerhub-front/src/; backend: packages/containerhub-back/src/; agente: packages/containerhub-agent/src/.

Regla para leer esta guía: «la pantalla permite» describe botones visibles según permiso; «el endpoint permite» describe la autorización en el servidor. Son capas distintas. Las afirmaciones son lectura de código, no prueba de operación en un cluster real.

Arranque y límites de seguridad

El backend llama a SetupContainerHub.ts antes de aceptar peticiones; inicializa conexiones/identidad y, si se habilita, el usuario inicial. index.ts crea Fastify, opcionalmente sirve el frontend compilado, inicia el manager de registros de tareas y abre el puerto. El recolector de métricas tiene una entrada separada: monitoring.ts. El agente es otro proceso: agent/src/server.ts.

El servidor en YogaFastifyServerFactory.ts registra REST, GraphQL, WebSocket, identidad, auditoría, ajustes e integraciones. Ejecuta middleware de JWT, API key y RBAC; cada ruta local sensible exige un permiso propio. GraphQL combina los archivos .graphql y .resolvers.ts de modules/ mediante GraphQLSchema.ts; la mayoría de pantallas operativas de esta guía llaman a REST. Ojo: YogaFastifyServer.ts instala un validador Fastify que siempre acepta; el esquema de OpenAPI no demuestra por sí solo que se valide la entrada. Hay que comprobar validación explícita en cada servicio.

En el navegador, main.ts prepara Pinia, entidades, i18n, Vuetify y el router; SetupEntities.ts registra las tablas. rest.ts agrega el token de acceso a llamadas REST. El router exige sesión válida y redirige si falta un permiso, pero la barrera efectiva está también en Fastify: ocultar un botón no protege el endpoint.

Inicio y navegación

Inicio / sesión

La portada HomePage.vue muestra la galería de HomeGallery.vue. Sus entradas nacen en navigation.ts; no es un inventario propio de Docker. App.vue reutiliza el mismo menú en el lateral, con perfil, cambio de tema y salida.

Navegación → guardia del router → componente de la página. Añadir una página requiere registrar ruta y, si debe aparecer en la interfaz, menú; definir solo el menú no crea su endpoint.

Login y administración de identidad

Login /login público

LoginPage.vue envuelve IdentityLogin de @drax/identity-vue; al entrar, vuelve a la ruta solicitada si el redirect es una ruta local válida. El guardia en router/index.ts verifica usuario, token y vigencia del JWT. El backend registra las rutas de identidad importadas de @drax/identity-back en YogaFastifyServerFactory.ts.

Usuarios, roles, claves API y sesiones administración

Las pantallas y rutas de identidad se importan de @drax/identity-vue mediante IdentityRoutes en router/index.ts; el menú en navigation.ts agrega Usuarios, Roles, Claves API y Sesiones. El proyecto excluye la ruta de tenants. Las rutas de servidor UserRoutes, RoleRoutes, UserSessionRoutes, UserLoginFailRoutes y UserApiKeyRoutes también vienen de Drax. No atribuir su lógica interna a archivos locales de ContainerHub.

Los roles asignan permisos; la UI pregunta hasPermission, mientras el servidor vuelve a comprobar con el middleware RBAC o requirePermission. Para entender una operación administrativa concreta hay que seguir el paquete Drax instalado, además de estos puntos de integración.

Auditoría /crud/audit audit:manage

La página AuditCrudPage y el descriptor AuditCrud proceden de @drax/audit-vue; el backend registra AuditRoutes de @drax/audit-back en YogaFastifyServerFactory.ts. Para mutaciones de servicios y redes, ContainerHub arma el contexto de auditoría en ServiceMutationAudit.ts. Si falla la persistencia de auditoría se registra el error, pero no se revierte la mutación Docker. No confundir este registro con los logs de consola de una tarea.

Stacks /stacks DOCKER_VIEW

StacksPage.vue usa la tabla de Drax; StacksCrud.ts obtiene GET /api/services, agrupa por la propiedad stack de cada servicio y cuenta miembros. El botón abre /services?stack=…. El backend obtiene servicios Docker en ServiceRoutes.ts → ServiceService.ts.

No hay un modelo «Stack» almacenado por esta página: la lista se deriva de los servicios devueltos. Si un stack no tiene servicios visibles, no aparece. No crea, edita ni elimina stacks; búsqueda, orden y CSV se resuelven en el navegador.

Servicios y tareas /services DOCKER_VIEW

ServicesPage.vue es una tabla operativa propia; ServiceCrud.ts define columnas, filtros y paginación mediante GET /api/services/paginate. Fastify ServiceRoutes.ts procesa la consulta y llama a paginateServices en ServiceService.ts. Al expandir una fila, la página carga tareas de ese servicio, estados y nodo.

Seleccionar servicios → confirmar reinicio/eliminación → POST /api/docker/service/restart o POST /api/docker/service/remove → servicio de Docker → resultados por servicio. La interfaz exige DOCKER_RESTART / DOCKER_REMOVE, y las rutas vuelven a exigirlos; el descriptor CRUD de listado no habilita un formulario de alta o edición.

El backend sí expone operaciones de creación/actualización y rutas auxiliares para compatibilidad; su existencia no implica que esta pantalla las ofrezca. Seguir ServiceMutationAudit.ts para quién/qué registra cada mutación. mapInspectToServiceModel.ts adapta datos crudos de Docker al contrato presentado. Las tareas retenidas no equivalen a réplicas actualmente en marcha.

Una tarea: inspección, métricas, logs y terminal

Inspección /inspect/:taskId DOCKER_VIEW

TaskInspectPage.vue pide GET /api/docker/task/:taskId/inspect, organiza la respuesta como árbol en taskInspectTree.ts y puede buscar el servicio relacionado para completar contexto. ServiceRoutes.ts pasa a fetchTaskInspect una opción de visibilidad: ver configuración sensible requiere además DOCKER_CONFIGURATION_VIEW. Leer una tarea no implica poder revelar sus secretos.

Estadísticas actuales /statistics/:taskId DOCKER_VIEW

TaskStatisticsPage.vue consulta GET /api/docker/task/:taskId/stats; taskStatistics.ts compone muestras y sparklines. El botón se muestra solo para tareas en ejecución con contenedor. La ruta del backend delega en fetchTaskStats; si la tarea vive en otro nodo, el camino atraviesa el agente. Los puntos de la gráfica son estado local de la UI mientras se consulta; para histórico persistido, ver Monitorización.

Logs en vivo /logs/:taskId DOCKER_LOGS

TaskLogsPage.vue abre /api/docker/task/:taskId/logs/stream por WebSocket. Envía filtros de tiempo, inclusión/exclusión, timestamps y número de líneas; ServiceRoutes.ts limita la cola según Ajustes y llama a streamTaskLogs. LogTerminal.vue representa el flujo. Cambiar filtros reconecta y limpia el visor; pausar cierra el socket, no detiene Docker. La página consulta también GET /api/settings, que requiere SETTINGS_SHOW; si no tiene ese acceso, continúa con el límite local.

Terminal interactiva /terminal/:taskId DOCKER_TERMINAL

La pantalla TaskTerminalPage.vue usa xterm: un POST autorizado entrega un ticket de un solo uso que vence a los 60 segundos; el navegador lo presenta por subprotocolo WebSocket a /api/docker/terminal. TerminalRoutes.ts comprueba origen, ticket y límites de tamaño/tiempo; el socket se autentica con el ticket, no con la cadena JWT/RBAC ordinaria. TerminalSessionService.ts custodia tickets en memoria de un proceso; el backend abre un exec en la tarea local o vía AgentTerminalClient.ts. Recargar directamente la página pierde el ticket del navegador. No es un shell del servidor web: ejecuta comandos en el contenedor de la tarea; su permiso es de alto riesgo.

Infraestructura Docker

Nodos /nodes DOCKER_NODES_FETCH

NodesPage.vue muestra el CRUD de NodesCrud.ts: GET /api/docker/nodes y filtros, orden, paginación y CSV en cliente. ServiceService.ts consulta Docker y compone rol, recursos, estado y salud del agente donde corresponda. Solo lectura; «agente no saludable» y «sin agente» no son lo mismo.

Redes /networks DOCKER_NETWORK_VIEW

NetworksPage.vue muestra datos de GET /api/docker/network mediante NetworksCrud.ts. La UI formatea creación, attachable y valores IPAM; filtros y CSV se aplican localmente. Router y endpoint requieren DOCKER_NETWORK_VIEW, aunque el descriptor CRUD declara DOCKER_VIEW: no son permisos equivalentes. Aunque ServiceRoutes.ts tenga endpoints de mutación de redes para otros clientes, esta pantalla no los expone.

Cluster /cluster DOCKER_VIEW

ClusterInformationPage.vue pide /api/docker/cluster para contadores y /api/docker/nodes-and-tasks para ClusterVisualizer.vue. RefreshOptions.vue activa refresco opcional del visualizador y selección de tareas en ejecución; el timer se cancela al salir y no vuelve a cargar el resumen. El contador de tareas incluye también tareas históricas retenidas por Docker, no solo activas.

Contenedores «fantasma» /ghost-containers DOCKER_VIEW

GhostContainersPage.vue usa GhostContainersCrud.ts y GET /api/docker/ghostContainers. El backend reúne contenedores en ejecución del manager y los workers disponibles, y excluye los asociados a tareas Swarm running cuyo ID de contenedor coincida. También descarta contenedores con etiquetas pero sin ID de tarea. Omite nodos que Docker informa down; si falla un agente de otro nodo, devuelve 503 en vez de una lista parcial. Muestra nodo, imagen y estado; busca y exporta CSV. La pantalla es solo lectura: leer la definición en ServiceService.ts antes de interpretar una fila como error.

Integraciones: Registry y GitLab

Imágenes Registry /registry-images DOCKER_VIEW

RegistryImagesPage.vue y RegistryImagesCrud.ts listan repositorios; al expandir, RegistryImageDetails.vue carga etiquetas/detalles de imagen y los relaciona con servicios desplegados. RegistryRoutes.ts sirve peticiones a través de RegistryService.ts. El Registry es externo: verlo aquí no implica que ContainerHub almacene esas imágenes.

Proyectos GitLab /gitlab-projects DOCKER_VIEW

GitLabProjectsPage.vue y GitLabProjectsCrud.ts listan proyectos; expandir consulta tags, y elegir uno muestra su pipeline asociado y despliegues que coinciden con servicios Docker. El enlace externo abre GitLab; el enlace interno abre el Registry. GitLabRoutes.ts delega en GitLabService.ts. Si falta token o falla GitLab, el contenido dependiente no se obtiene: no confundir integración caída con ausencia real de proyectos.

Monitorización: configuración, muestras e historial

Monitoreos /monitoring DOCKER_VIEW

MonitoringPage.vue lista configuraciones, permite seleccionar servicios e intervalo/tipo/período y, con permisos específicos, crear, pausar, reanudar o borrar. MonitoringCrud.ts es el contrato de tabla y provider; MonitoringRoutes.ts autoriza y valida cada operación; MonitoringService.ts conserva configuraciones en la base configurada.

Crear configuración → persistir → monitoring.ts inicia el proceso separado → MonitoringWorker.ts espera señales de cierre → MonitoringCollector.ts consulta configuraciones cada segundo y, cuando corresponde por estado, fecha e intervalo, obtiene estadísticas y guarda muestras. Crear una fila no es una medición instantánea. El recolector puede usar el agente para tareas remotas; su próxima ejecución por configuración vive en memoria del proceso.

Historial /monitoring/:id DOCKER_VIEW

MonitoringHistoryPage.vue pide configuración y /api/monitoring-configurations/:id/samples. Envía rango y límite al servidor; filtra la tarea entre las muestras ya recibidas. Convierte bytes y construye gráficos SVG de CPU, memoria, I/O y red. MonitoringRoutes.ts → MonitoringSampleService.ts. El gráfico muestra muestras almacenadas sin refresco automático; no garantiza continuidad si el recolector estuvo apagado.

Historial de tareas /tasks-monitorization DOCKER_VIEW

TasksMonitorizationPage.vue y TaskMonitorizationCrud.ts consultan GET /api/task-monitorizations con paginación del servidor. TaskMonitorizationManager.ts sondea tareas Swarm, genera registros running/removed, los guarda y poda según Ajustes. modifiedBy se infiere de auditorías recientes: es una heurística, no una atribución demostrada. Es un historial de ciclo de vida de tareas, distinto de las muestras de rendimiento; la página es solo lectura.

Configuración /settings SETTINGS_SHOW

SettingsPage.vue carga y guarda por SettingsApi.ts → GET/PUT /api/settings en SettingsRoutes.ts → SettingsService.ts. Los campos son máximo de líneas de logs, número de tareas retenidas e intervalo de monitorización de tareas. La lectura requiere SETTINGS_SHOW; guardar requiere SETTINGS_UPDATE, incluso si la página se puede abrir sin este último.

No son variables Docker Compose: son ajustes de aplicación leídos por rutas y procesos. Cambiar un campo en el navegador no actualiza el YAML de despliegue.

Cómo seguir el código sin perderse

Si necesitas…Empezá por…Después comprobá…
Agregar una páginarouter/index.ts y navigation.tsPermiso y endpoint en el servidor; traducciones e identificación en SetupEntities.ts si usa tabla.
Cambiar un listadoEl Page.vue y su cruds/*Crud.tsSi el filtrado/paginación es cliente (Stacks, Nodos, Redes) o servidor (Servicios, Monitoreos, Historial de tareas).
Cambiar DockerServiceRoutes.ts y ServiceService.tsPermisos, normalización Docker y acceso a agente en worker; no confiar solo en la UI.
Cambiar acceso/seguridadYogaFastifyServerFactory.ts y paquete Drax de identidadGuardia visual, middleware y permiso del endpoint específico; sin agregar secretos al HTML.
Cambiar recolecciónmonitoring.ts, MonitoringWorker.tsPersistencia de configuración y muestras, cadencia del proceso separado y tareas remotas.

Alcance de la evidencia: inspección de fuentes y enlaces locales del árbol de trabajo. Este documento no ejecuta peticiones a Docker, Mongo, GitLab o Registry, ni prueba permisos desde un navegador autenticado. Los paquetes Drax aportan implementación que no está reexplicada aquí; las dependencias se identifican por sus puntos de integración locales. Ningún secreto se incluye en el documento.
