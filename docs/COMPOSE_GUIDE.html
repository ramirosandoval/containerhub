ContainerHub: entender el docker-compose.yml

Revisión: 23 de septiembre de 2026 · Archivo de referencia: compose actual.

Idea central: este YAML describe tres servicios Swarm: la aplicación, el recolector de métricas y un agente por worker Linux. No se ejecuta con docker compose up; el despliegue usa docker stack deploy desde un manager. Un stack llamado dockerway alberga además otros servicios: no desplegar este archivo parcial encima de ese stack compartido. Docker: desplegar stacks.

Mapa en 30 segundos

navegador → :9998 → containerhub (manager): API + frontend compilado
                         │ Docker socket local
                         ├─ overlay externa → Mongo (datos) y Vault (secretos)
                         └─ overlay de agentes → containerhub-agent :9997 (workers)
containerhub-monitoring (manager, sin puerto público)
                         ├─ Mongo: lecturas y muestras de métricas
                         ├─ Docker socket: tareas locales
                         └─ agentes: estadísticas de tareas remotas

El agente consulta el Docker daemon del nodo donde corre; por eso es global en workers. La aplicación usa el socket del manager para el trabajo local y DNS de Swarm para hallar al agente de cada worker; dnsrr devuelve direcciones de tareas en vez de una IP virtual única. Docker: DNSRR. Fuente del cliente: packages/containerhub-back/src/modules/services/services/AgentHealthClient.ts.

Qué hace cada bloque

«Verificar» significa observar configuración o estado, no demostrar que la función completa opera. Un parser de YAML no prueba login ni comunicación con workers.

Variables, una por una

La forma ${VARIABLE:-valor} toma la variable del entorno del comando o usa el fallback si está ausente/vacía. Docker: interpolación. Lo siguiente describe este YAML, no todos los modos de arranque del backend.

En este archivo no hay servicio Redis, Mongo ni Vault: los dos últimos se alcanzan por la red externa; Redis no es dependencia declarada aquí. La ausencia de un servicio en este YAML no prueba que no exista en el stack compartido.

Operar sin sorpresas

  1. Antes de desplegar en un stack aislado, comprobar que las dos imágenes están disponibles en los nodos elegibles, que existe la overlay externa, que existe el Docker secret y que cada nodo tiene los bind mounts requeridos. En este archivo external: true significa que Docker no crea el secret por ti. Docker: secrets externos.
  2. Fijar CONTAINERHUB_ORIGIN a la URL real del navegador (HTTPS detrás de proxy en un entorno compartido), el puerto, la URI de Mongo correcta y los roots reales. El bootstrap está deshabilitado por defecto; para crear el primer usuario, habilitarlo explícitamente y configurar su identidad y secreto en Vault antes del despliegue.
  3. Inspeccionar con comandos de solo lectura; estos evitan imprimir valores de variables o secretos:
docker compose -f docker-compose.yml config -q
docker stack config -c docker-compose.yml >/dev/null
docker stack services dockerway --format '{{.Name}} {{.Replicas}}'
docker node ls --format '{{.Hostname}} {{.Status}}'
docker secret inspect containerhub-vault-client-key --format '{{.Spec.Name}}'

Un cambio del servicio real requiere aprobación y ventana, no una aplicación automática de este YAML al stack compartido. Tras un despliegue autorizado verificar por separado: servicio app/collector corriendo, login con usuario existente, persistencia de una muestra, agente en worker distinto y terminal desde navegador. El render del compose solo prueba sintaxis; no demuestra esas capas.

Estado y deuda, no tareas silenciosas: el 23/09/2026 debianvm estaba Down y el agente 0/0, así que no se comprobó el camino remoto. El token GitLab que se retiró era de prueba, expirado y nunca pusheado según el usuario: no se planifica revocación. README.md y docs/DEPLOYMENT.md describen además otros modos de instalación; verificar la sección de stack antes de operar. El agente hoy usa HTTP/WS sin mTLS; la overlay no lo vuelve autenticado. El socket Docker conserva privilegios altos; Mongo legacy y mounts relativos adicionales no están cubiertos automáticamente.

También se quitó docker-compose.override.yml: agregaba servicios app y agent que no forman parte de este stack. Antes, docker compose config --services enumeraba cinco; ahora enumera solo estos tres. El stack siempre se invocaba con -c docker-compose.yml, así que ese override no formaba parte de su definición. Docker: combinación automática de archivos Compose.

Fuentes y naturaleza de la evidencia

Repositorio: YAML actual, Dockerfile, packages/containerhub-agent/src/server.ts, packages/containerhub-back/src/setup/VaultSecretLoader.ts y los tres YAML de docker-fortes citados arriba. Plataforma: Docker Stack, Swarm mounts, DNSRR, host publish, secrets e interpolación. Runtime observado: inventario de servicios/nodos y validación del YAML; no hay prueba UI ni E2E de worker.
