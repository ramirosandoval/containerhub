## Hallazgos

### B04-001 — seguridad / límite de confianza — alta — comprobado
- Evidencia: `packages/containerhub-back/src/modules/registry/routes/RegistryRoutes.ts:21` pasa `request.query.name` a `fetchImageTags`; `packages/containerhub-back/src/modules/registry/services/RegistryService.ts:1-10,20-23` interpola ese nombre sin validación/codificación y usa `new URL(path, REGISTRY_URL)`. Reproducción aislada con `fetch` mock: con base `https://registry.local/v2/`, `name=https://example.invalid/path` intenta `https://example.invalid/path/tags/list`; `name=../secret` intenta `https://registry.local/secret/tags/list` (no hubo red real). El permiso Docker View limita quién lo invoca (`RegistryRoutes.ts:6-8`), pero no el destino del request.
- Impacto: un cliente con ese permiso puede hacer que el backend emita GET hacia otro host o ruta fuera de `/v2/` (SSRF y salida del alcance del Registry configurado); no se demostró accesibilidad a hosts internos ni respuesta efectiva de una red real.
- Contraste: `RegistryService.test.ts:51-57` comprueba rechazo de rutas inseguras sólo en `fetchImageDetails`, que usa `encodedRepository` (`RegistryService.ts:32-41`); no hay prueba de `fetchImageTags` con nombre host/ruta maliciosa.
- Intervención mínima: reutilizar `encodedRepository(name)` en `fetchImageTags` y mantener una prueba con mock de `fetch` que rechace `../`/URL absoluta antes de emitir requests.

### B04-002 — completitud de datos / paginación Registry — media — comprobado
- Evidencia: `packages/containerhub-back/src/modules/registry/routes/RegistryRoutes.ts:20-21` usa `rows='1000'` por defecto para catálogo y expone tags; `packages/containerhub-back/src/modules/registry/services/RegistryService.ts:15-23` hace sólo una petición por listado y devuelve la primera página, ignorando `Link: …; rel="next"`. `packages/containerhub-front/src/cruds/RegistryImagesCrud.ts:18-35` pagina **en cliente** sólo el array recibido. La [especificación oficial Distribution, Listing Repositories/Pagination](https://distribution.github.io/distribution/spec/api/#listing-repositories) define `Link` para catálogo; [Listing Image Tags/Pagination](https://distribution.github.io/distribution/spec/api/#listing-image-tags) prevé el mismo mecanismo para tags. Un `fetch` mock con una página de catálogo `{repositories:['first']}` y `Link: rel="next"` produjo sólo `first` y exactamente una petición.
- Impacto: si el Registry envía una página siguiente, las imágenes posteriores no aparecen en listado/búsqueda/exportación y los tags posteriores no aparecen en detalles (`packages/containerhub-front/src/components/RegistryImageDetails.vue:101-107`); un catálogo sin entrada no prueba ausencia del repositorio, ya que el Registry puede limitar visibilidad.
- Contraste: `packages/containerhub-back/src/modules/registry/services/__tests__/RegistryService.test.ts:8-57` cubre detalles, no `fetchImages`, `fetchImageTags` ni paginación real.
- Intervención mínima: seguir el `Link` de continuación hasta terminar para ambos listados, conservando origen/ruta permitidos; probar con dos páginas mock. Si el producto sólo pretende primeras N imágenes, explicitar ese contrato en API/UI en vez de presentar paginación local como catálogo completo.

### B04-003 — completitud de datos / paginación GitLab tags — media — comprobado
- Evidencia: `GitLabRoutes.ts:26` → `GitLabService.ts:77-79` emite un GET de `projects/:id/repository/tags` y retorna directamente una página. La [API oficial GitLab Tags, List all project repository tags](https://docs.gitlab.com/api/tags/#list-all-project-repository-tags) ofrece `page` (por defecto 1) y la [paginación REST oficial](https://docs.gitlab.com/api/rest/#offset-based-pagination) aplica `per_page` por defecto 20. `GitLabProjectsPage.vue:190` trata la respuesta como lista de tags para seleccionar; `:220` sólo consulta pipeline del tag elegido.
- Impacto: proyectos con tags en páginas posteriores no pueden seleccionarlos en esa vista, aunque la consulta individual del pipeline acepte su nombre.
- Contraste: `GitLabService.test.ts:12-89` no invoca `fetchProjectTags`; `GitLabRoutes.test.ts:5-15` sólo revisa texto de rutas.
- Intervención mínima: paginar tags hasta agotar el `Link`/siguiente página, o exponer paginación al consumidor si listar todos los tags resulta costoso; probar al menos dos páginas mock.

### B04-004 — contrato de conteo GitLab — media — comprobado
- Evidencia: `GitLabService.ts:66-75` convierte cabecera `x-total` ausente en `0` aunque `items` contenga proyectos; `GitLabProjectsCrud.ts:25-31` entrega ese cero como `total` al paginador. Reproducción mock: respuesta `[{"id":1}]` sin cabecera → `{totalItems:0,items:[{"id":1}]}`. La [documentación oficial GitLab, Pagination response headers](https://docs.gitlab.com/api/rest/#pagination-response-headers) indica que para consultas de más de 10.000 registros no devuelve `x-total`; también advierte que en GitLab.com algunas cabeceras pueden faltar ([Other pagination headers](https://docs.gitlab.com/api/rest/#other-pagination-headers)).
- Impacto: el paginador muestra total cero con elementos presentes y puede ocultar navegación; no se verificó su comportamiento UI real.
- Contraste: `GitLabService.test.ts:12-28` sólo suministra `x-total:1` y confirma el camino feliz; no prueba cabecera ausente.
- Intervención mínima: no representar cabecera ausente como cero conocido; modelar total desconocido y ajustar paginación/consumidor (o contar mediante mecanismo documentado) con prueba mock de cabecera ausente.

### B04-005 — invariante singleton Mongo — media — probable
- Evidencia: `SettingsMongoRepository.ts:4-9,12-23` hace `findOne` y después `create({})`/`new Settings().save()` sin identificador fijo; `Settings.ts:9-17` no declara clave única para la fila. Dos primeras lecturas concurrentes pueden observar vacío antes de insertar ambas. En contraste, `SettingsSqliteRepository.ts:16-24,29-33` usa `_id='1'`.
- Impacto: dos documentos de ajustes podrían divergir; posteriores `findOne`/actualizaciones pueden operar sobre cualquiera y devolver configuración distinta a rutas/monitorización (`ServiceRoutes.ts:47-49`; `TaskMonitorizationManager.ts:42-46`). No se reprodujo carrera con Mongo real ni se afirma que ocurra en despliegue normal.
- Contraste: `SettingsService.test.ts:6-23,27-52` sustituye modelo y sólo prueba validación; `SqlitePersistence.test.ts:9-21` prueba SQLite, no Mongo; no se localizó prueba de concurrencia Mongo.
- Intervención mínima: imponer identidad única y crear/actualizar mediante operación atómica con upsert; probar carreras contra Mongo de prueba antes de afirmar corrección.

### B04-006 — errores de entrada Registry — baja — comprobado
- Evidencia: `RegistryRoutes.ts:21-22` entrega parámetros ausentes al servicio; `RegistryService.ts:20-22,39-41` lanza `Error` genérico y `YogaFastifyServer.ts:9-10` anula la validación declarativa. Una inyección Fastify aislada con RBAC simulado a `GET /api/registry/image/tags` y `GET /api/registry/image/details`, sin query, devolvió `500 name is required` y `500 reference is required` respectivamente, sin llamar a Registry.
- Impacto: peticiones mal formadas se atribuyen a fallo servidor en lugar de un error de cliente verificable, dificultando diagnóstico/alertas; no hay fallo de disponibilidad comprobado.
- Contraste: `RegistryService.test.ts:51-57` prueba rechazos directos de detalles, no códigos HTTP; no se localizó test de rutas Registry.
- Intervención mínima: validar parámetros requeridos en límite HTTP y responder 400/422 según convención existente, con una prueba de `inject` sin credenciales reales.
