## Hallazgos

### B01-001 — validación de entrada — alta — comprobado
- Evidencia: `packages/containerhub-back/src/servers/YogaFastifyServer.ts:9-10` instala un compilador que acepta **todo** esquema; caller `YogaFastifyServerFactory.ts:61-62` → rutas, p. ej. `modules/services/routes/TerminalRoutes.ts:68-75` declara longitud máxima 128 para `taskId` pero `createTerminalSession` (`:61-64`) sólo comprueba identidad y shell. La ruta de settings (`modules/settings/routes/SettingsRoutes.ts:18-25`) sí delega parseo Zod a `SettingsService.ts:23-32`, por lo que no se generaliza ausencia total de validación.
- Impacto: rutas que dependen sólo de JSON Schema no rechazan entrada inválida antes de su handler; tampoco hay coerción de query. El límite `taskId` declarado no se aplica por Fastify en el servidor de producción, aunque el shell sí se comprueba en código. No implica por sí solo bypass de autenticación ni explotación demostrada.
- Contraste: `servers/__tests__/YogaFastifyServer.test.ts:5-25` afirma expresamente la aceptación de `page=0` contra un esquema `minimum:1`; `modules/services/routes/__tests__/TerminalRoutes.test.ts:128-141` monta **otro Fastify sin el compilador permisivo**, por lo que su 400 no verifica esta factoría. Tests leídos, no ejecutados.
- Intervención mínima: conservar la compatibilidad documental donde se requiera, pero añadir validación local de los campos que sólo confían en el esquema (empezando por `taskId`) y test con `YogaFastifyServerFactory`; no activar indiscriminadamente validación global sin revisar rutas Drax.

### B01-002 — límite de transporte de secretos — media — comprobado
- Evidencia: `packages/containerhub-back/src/setup/VaultSecretLoader.ts:23-25,42-52` acepta `CONTAINERHUB_VAULT_URL` como URL base sin exigir HTTPS; `fetch` envía `clientid/clientkey` y recibe secretos por el esquema configurado. Caller `SetupContainerHub.ts:148-150` antes de cargar configuración Drax. El test `setup/__tests__/VaultSecretLoader.test.ts:8-45` utiliza una URL `http:` simulada, no prueba tráfico ni red.
- Impacto: **si se configura HTTP sobre una red no protegida**, credencial del cliente y secretos cruzan ese límite sin TLS; no se afirma que el despliegue real use tal red. La variable permite también HTTPS.
- Intervención mínima: exigir HTTPS en producción o documentar y comprobar el límite de transporte seguro que justifique HTTP; añadir test de rechazo/aceptación por entorno sin llamar a Vault real.

### B01-003 — duplicación de permisos semilla — baja — comprobado
- Evidencia: `packages/containerhub-back/src/setup/SetupContainerHub.ts:49-56` define el conjunto de permisos de identidad para `CreateOrUpdateRole` (`:57-81`), mientras `LoadPermissions` mantiene una segunda enumeración manual de la misma familia (`:160-173`). Caller `index.ts:6` → setup → registro/siembra Drax.
- Impacto: al añadir o renombrar una concesión hay que coordinar dos listas; una divergencia dejaría permiso registrado sin asignar (o viceversa). No se observó divergencia funcional actual; `LegacyDockerRoles.test.ts:27-108` verifica bundles seleccionados y autorización, no igualdad exhaustiva de ambas listas.
- Intervención mínima: elevar el array ya existente al módulo y reutilizarlo en ambos puntos, manteniendo separadas las concesiones adicionales de settings/Docker.
